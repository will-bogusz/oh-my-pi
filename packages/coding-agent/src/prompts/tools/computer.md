Control real host application windows from JavaScript or Python Eval with `computer` (not `browser`; no DOM). Safety rules: system prompt.

<instruction>
- Flow: `await computer.window(selector, { launch?, screenshot?, silent?, maxDepth?, maxElements?, query? })` acquires ONE exact window and displays its background inspection (tree and image); `win.initialObservation` holds that snapshot (`inspectionError` when AX failed). Loop: act on a ref → observe → verify. Acquisition never focuses anything.
{{#if linux}}
- Identity: `selector` is an exact id or `{ app?, title?, id?, pid? }` and must resolve exactly one window; ambiguity returns candidates — pick an exact `id`/`pid`, never a name guess. `computer.windows(filter)` lists without inspecting; `computer.window({ app }, { launch: true })` launches that app by executable name or path and acquires its window in one call — use it instead of launch-then-acquire; `computer.launch(nameOrPath | { name?, urls?, newInstance? })` launches in the background without acquiring (`bundleId` is macOS-only and ignored here). A window whose owner advertises no process id is not listed: nothing can address it.
- Observe: `win.observe(options)` → `{ snapshotId, window, tree, elements, complete, backgroundInput, relatedWindows?, documentPath?, documentEdited?, screenshot?, screenshotError? }`. `screenshot:false` is tree-only. The tree is the app's AT-SPI tree: GTK and Qt publish it natively, Chromium/Electron need `--force-renderer-accessibility`, and a window whose app publishes no AT-SPI provider returns a single frame element — work from the screenshot then. `complete:false` = partial tree: returned refs are valid, omitted controls unknown — widen `maxElements` or `win.find({ role?, label?, value?, limit? })`. Any `maxElements` you set is a budget the walk may have hit, so it reports `complete:false` unless the driver proves the walk finished; omit it to ask for the whole tree.
{{else}}
- Identity: `selector` is an exact id or `{ app?, title?, id?, pid? }` and must resolve exactly one window; ambiguity returns candidates — pick an exact `id`/`pid`, never a name guess. `computer.windows(filter)` lists without inspecting; `computer.window({ app }, { launch: true })` launches that app and acquires its window in one call — use it instead of launch-then-acquire; `computer.launch(nameOrPath | { bundleId?, name?, urls?, newInstance? })` launches in the background without acquiring.

Any `maxElements` you set is a budget the walk may have hit, so it reports `complete:false` unless the driver proves the walk finished; omit it to ask for the whole tree.
{{/if}}
- Elements from `observe`/`find` carry snapshot data (`ref`, `role`, `label`, `value?`, `enabled?`, `actions?`, `bounds?`, and `help?`/`description?` — the provider's own account of what the control does, when it wrote one) and methods `click`, `doubleClick`, `setValue`, `type`, `press`, `scroll`, `perform(action)`. `win.ref(token)` is a handle for those methods (`await win.ref(r).click()`); `await win.ref(r)` returns the snapshot. Activate with `click()`.
- Window actions: `click(token | [x,y], { button?, count?, modifiers?, delivery? })`, `doubleClick`, `drag(token | [x,y], token | [x,y], { delivery: "foreground" })`, `scroll(direction, { target?, amount?, by? })`, `type(text, { target? })`, `press(chord, { target? })`, `setValue(token, text)`, `setFrame(bounds)`, `menu(path, { delivery: "foreground" })`, `reveal()`, `verify(expectations, { timeoutMs?, stableSamples? })`.
- Refs are short ids (`n7`) minted by each observation and bound to that exact window id/pid; observing a window again retires its previous refs. `observe`, `find` and `verify` refresh them. On `StaleRef` re-observe; never guess tokens. Pixels belong to the latest image of the SAME window; AX `bounds` are global desktop coordinates — never mix. `modifiers` or a `count` on a ref click, and either end of a `drag`, is delivered at the ref's own bounds as a pixel action, so that window needs a current screenshot (`observe({ screenshot: true })`); a ref with no bounds and no frame is refused.
{{#if linux}}
- Actions return `{ text, effect, evidence, data?, route?, delivery }`. Dispatch is not proof: read the postcondition back via fresh observation or `verify`. A failed reply may still have acted — inspect before retrying. Here `effect: "unverifiable"` is the ordinary shape of a successful action: the driver delivered and has no post-condition proof. It is not a failure and never a reason to repeat the action — verify by re-observing. `confirmed` means the intended state was read back; `suspected_noop` is a positive reason to believe nothing happened. `setValue` never reaches disk and does not mark the document edited, so `documentEdited: false` after a `setValue` is not proof of a save: in document apps save through the app (menu or `type`+shortcut), then confirm on disk or via `documentEdited`.
- Delivery defaults to background; the runtime never escalates on its own. Background is the AT-SPI route: element `click` and `setValue` reach GTK, Qt, Chromium and WebKitGTK without touching focus. Synthetic keys and pixel coordinates have no background route into those toolkits, so `press`, `type` at a terminal window and pixel targets take `delivery: "foreground"` — a first-class route on this backend, not a last resort: it raises the target, delivers real input, and needs a running window manager (without one the driver refuses with `foreground_unavailable`). A `background_unavailable` refusal means nothing was dispatched at all, so retrying that exact action with `{ delivery: "foreground" }` is safe and is the intended next step. `computer.displays()` and desktop-root input (`computer.click/doubleClick/move/drag/scroll/type/press`) are unsupported here: the driver reports no display identity. `reveal()` only when the user should see the window — never for screenshots or recovery. Never fall back to `xdotool`, `wmctrl`, `xclip` or a shell launcher.
- Interruptions: nothing is refused for you on this backend and `interruptedBy` is never set — there is no system-owned window layer to sample, so a credential prompt or lock screen is just another window. If a screenshot or tree shows a password prompt, an unlock screen or any dialog you did not open, stop, tell the user what is asking, and never type or click at it.
- Lifecycle: a supervised `cua-driver` child runs native control over X11 and AT-SPI. Cancelling stops the in-flight action and reports what landed as `partial`; refs survive unless the child was replaced. `await computer.release()` when done (automatic at turn settle); later calls start a fresh child — reacquire windows. That child owns the clipboard selection it wrote, so `computer.clipboard.write` content lasts only while the session is held: paste it before releasing. `computer.close()` ends computer use for this session.
{{else}}
- Actions return `{ text, effect, evidence, data?, route?, delivery }`. Dispatch is not proof: read the postcondition back via fresh observation or `verify`. A failed reply may still have acted — inspect before retrying. `effect` is the driver's own read on delivery, not on your goal: `confirmed` (intended state read back), `unverifiable` (dispatched; `evidence [{ kind: "window_change" }]` means the target did react), `suspected_noop` (positive reason to believe nothing happened — the element never advertised the action, or nothing about the target changed after delivery). A background element click reaches the app as an AX press or a PID-routed event, and neither carries trusted pointer events, so a control driven by `pointerdown` (common in Chromium/Electron UIs) ignores it and reports `suspected_noop`: do not repeat it — screenshot the window and click that control's pixel center with `delivery: "foreground"`, which is the only rung that delivers real pointer events. `setValue` never reaches disk and does not mark the document edited, so `documentEdited: false` after a `setValue` is not proof of a save: in document apps save through the app (menu or `type`+shortcut), then confirm on disk or via `documentEdited`.
- Delivery defaults to background; the runtime never escalates on its own. Pass `delivery: "foreground"` yourself when the action needs it (drag, desktop-root input `computer.click/doubleClick/move/drag/scroll/type/press`, `menu`, a window that refuses background input) — it briefly makes the target key and restores focus after, so use it when the user asked for the result and background cannot deliver it. Do not send synthetic keys or clicks at a window that is not key unless `backgroundInput` confirms a route; in Electron click the editor first. `reveal()` only when the user should see the window — never for screenshots or recovery. Never fall back to shell `open` or AppleScript.
- Interruptions: while an `auth`, `permission` or `lock` window (password/TCC prompt, crash alert, lock screen) is on screen, every mutation is refused with `Interrupted:` and `interruptedBy { app, pid, windowId, title, kind }`; observations carry the same field. STOP: never type, click or send keys at it. Observe that window, tell the user what is asking, and wait. One exception: a crash alert for an app YOU launched that exited — do not relaunch; observe the alert, press its "Ignore" button, then tell the user.
- Lifecycle: a supervised `cua-driver` child (macOS) runs native control. Cancelling stops the in-flight action and reports what landed as `partial`; refs survive unless the child was replaced. `await computer.release()` when done (automatic at turn settle); later calls start a fresh child — reacquire windows. `computer.close()` ends computer use for this session.
{{/if}}
- Keys: `press("cmd+shift+d")` — modifiers {{#if linux}}`shift|ctrl|control|alt|super|meta|win` ({{else}}`cmd|command|shift|option|alt|ctrl|control|fn` ({{/if}}`cmd`/`super`, `option`/`alt` and DOM `Arrow*` names are translated for you); keys `return|enter`, `escape|esc`, `tab`, `space`, `backspace`, `delete`, `home`, `end`, `pageup`, `pagedown`, `up|down|left|right`, `f1`–`f12`, single characters. Anything else is not a key name — a wrong one can type its base key alone instead of failing.
- `computer.run(fnOrCode, { args?, read_only?, timeout? })` receives `{ desktop, wait, assert }`; closures are not captured; full host access, not a sandbox. Python: same names with keyword options; `run` takes JavaScript strings.
</instruction>

<examples>
```javascript
const win = await computer.window({ app: "Code" });
const search = win.initialObservation?.elements.find(el => el.label === "Search");
if (!search) throw new Error("Search control not exposed");
display(await win.click(search.ref));
await win.observe({ screenshot: false });
```
</examples>
