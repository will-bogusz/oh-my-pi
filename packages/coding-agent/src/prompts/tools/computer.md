Control real host application windows from JavaScript or Python Eval with `computer` (not `browser`; no DOM). Safety rules: system prompt.

<instruction>
- Flow: `await computer.window(selector, options)` acquires ONE window and prints its background inspection into `win.initialObservation`; then act on a ref → observe → verify. Acquisition never focuses anything.
- Selector: a window id or `{ app?, title?, id?, pid? }`. An `{ app }` with no window yet is launched and acquired in one call (`launch` defaults true; `{ launch: false }` refuses). Several matches → the frontmost, others named in the result: take one by exact `id`/`pid`, or `{ ambiguous: "throw" }` to be refused instead. `computer.windows(filter)` lists without inspecting; `computer.launch(name)` only launches.
- `win.observe(options)` prints the tree and returns `elements`; no screenshot unless asked (`{ screenshot: true }`), and neither it nor `find` discards an image you hold: pixels stale only when the frame moves. `complete: false` = the walk hit a cap: its refs are valid, omitted controls unknown; raise `maxElements` (omit for the whole tree) or `win.find({ role?, label?, value? })`, matching case-insensitive substrings (`{ exact: true }` for equality). A sheet on the target prints as `Attached sheets`: acquire it by id to drive it.{{#if linux}} The tree is the app's AT-SPI tree: GTK and Qt publish it, Chromium and Electron need `--force-renderer-accessibility`, an app publishing none yields one frame element — work from the screenshot.{{else}} Menu bars are excluded (`{ menubar: true }` includes them): an `AXMenuBarItem` press lands only while its menu is already open, so route menus through `menu(path, { delivery: "foreground" })`.{{/if}}
- Elements expose `click`, `doubleClick`, `setValue`, `type`, `press`, `scroll`, `perform(action)` and carry the provider's own `help`/`description`; `win.ref(token)` is that handle, awaited alone it returns the snapshot. The window takes those verbs plus `drag`, `setFrame`, `verify(expectations)`.
- Refs are short ids (`n7`) minted per observation and bound to one window: observing retires the previous set; `StaleRef` → re-observe, never guess. Pixels belong to the latest image of the SAME window, AX `bounds` are global desktop coordinates: never mix. `modifiers`, a `count`, or either end of a `drag` deliver at the ref's bounds as pixel actions, so that window needs a current screenshot; no bounds and no frame → refused.
- Dispatch is not proof: read the postcondition back by observing or `verify`, and inspect a failed reply — it may still have acted. `confirmed` = state read back. {{#if linux}}`effect: "unverifiable"` is the ordinary shape of success here — delivered without post-condition proof, never a reason to repeat the action.{{else}}`unverifiable` = delivered, and `evidence [{ kind: "window_change" }]` means the target reacted.{{/if}} `suspected_noop` = positive reason to believe nothing happened{{#if linux}}.{{else}}: a `pointerdown`-driven control (common in Chromium/Electron) ignores a background AX press — screenshot and click its pixel centre with `delivery: "foreground"`, the only route with real pointer events.{{/if}}
- `setValue` writes the AX value, never disk: `documentEdited: false` after one is no proof of a save — save through the app (menu or `type` its shortcut), then confirm.{{#if linux}}{{else}} `committed: false` = the app's own end-of-edit gesture did not run: re-read the field before building on it, and `type` the value when it stays uncommitted.{{/if}}
- Delivery defaults to background; the runtime never escalates on its own. Pass `delivery: "foreground"` yourself when the route needs it (drag, `menu`, desktop-root input, pixel targets, keys at a window that is not key); never for screenshots or recovery, and `reveal()` likewise.{{#if linux}} Background is the AT-SPI route: element `click`/`setValue` reach GTK, Qt and Chromium without touching focus, while synthetic keys and pixels need foreground, which raises the target and wants a running window manager (else `foreground_unavailable`). Foreground is first-class here, not a last resort: a `background_unavailable` refusal means nothing was dispatched, so retry it with `{ delivery: "foreground" }`. `computer.displays()` and desktop-root input are unsupported here.{{else}} Foreground briefly makes the target key and restores focus after. Check `backgroundInput` before sending keys, and in Electron click the editor first.{{/if}}
- Interruptions: never type, click or send keys at a password prompt, unlock screen, permission sheet, crash alert, or any dialog you did not open — observe it, tell the user what is asking, wait.{{#if linux}} Nothing is refused for you here and `interruptedBy` is never set.{{else}} An `auth`, `permission` or `lock` window (password/TCC prompt, crash alert, lock screen) refuses every mutation with `Interrupted:` and `interruptedBy`. Exception: a crash alert for an app YOU launched that exited — do not relaunch; press "Ignore", tell the user.{{/if}}
- Lifecycle: `computer.release()` (automatic at turn settle) ends the driver child, so a later call reacquires windows; cancelling reports what landed as `partial`.{{#if linux}} That child owns the selection it wrote: `computer.clipboard.write` lasts only while the session is held, so paste before releasing.{{/if}} `computer.close()` ends computer use for this session.
- Keys: `press("cmd+shift+d")` — modifiers {{#if linux}}`shift|ctrl|alt|super|meta`{{else}}`cmd|shift|option|ctrl|fn`{{/if}}; `cmd`/`super`, `option`/`alt` and DOM `Arrow*` names are translated. Anything else is not a key name: a wrong one can type its base key alone instead of failing.
- `computer.run(fnOrCode, options)` receives `{ desktop, wait, assert }`; no closures; full host access, not a sandbox. Python: same names, keyword options, JavaScript strings only.
</instruction>
